## 1. Stage plan 模板

每个 stage 一份 `specs/plan/1NN_stage<N>_<名>.md`。九节，缺一节就有一类问题会漏出去。

### 1.1 前置

- 上一 stage 的 DoD 已达成（贴出验收输出，不是"我记得过了"）
- **本 stage 依赖的未决项已裁**——逐条列出并给出裁决结果

> 这一节是最容易省略也最贵的。架构文档 §8 有一串「未决」，若某条正好是本 stage 的输入而没先裁，AI 会在中途自己替你裁一个，然后你要到三个 stage 之后才发现走岔了。

### 1.2 范围

**做什么**：清单，每条可勾。
**明确不做什么**：把下一个 stage 的内容、以及本 stage 容易顺手带出的东西写出来。

> 「不做什么」比「做什么」更能防跑偏——AI 的默认倾向是把看起来相关的都做掉。

### 1.3 代码结构与功能深度

- 落在哪些包、哪些新模块，与 001 §2 的依赖图是否一致
- **功能深度的取舍**：这个 stage 做到哪一档就停。例如表格做到 L1 不做 L2、锚点先用固定参数不做标定
- 新增的对外暴露面（preload / 包依赖 / 配置字段）——**必须预先声明**，事后才发现就是架构侵蚀

### 1.4 harness 增量

- 本 stage 新增哪几条检查，各自属阶梯的哪一层（002 §1）
- 有没有可以从 lint 升级到类型的（002 §2.1）
- 本 stage 的纪律硬度：不变量级 / 纪律级 / 约定级（002 §5.3）

### 1.5 自动化验证

- 新增单测清单
- 新增 smoke 清单
- **新增检查的反向验证**：每条新检查都要「故意违规 → 必须 FAIL → 撤销」，并贴输出。**这条不做，检查很可能是空转的**（002 §6.2）
- **跑出「破坏后仍绿」不是运气差，是检查空转的信号**：**先改检查、再重跑破坏**，把首轮结果与修复一并记入本节；`dead_checks` 记**首轮**空转数（口径见 §3.2，来历见 140 §1.5——九条检查首轮两条空转，都是这么抓出来的）
- `bun run check` 的最终输出

### 1.6 人工验证

机器判定不了的，列成可勾清单。**每条必须是具体动作 + 具体预期**，不能是「体验流畅」这种。

例如 Stage 2 的人工项：

- [ ] 用拼音连续输入 200 字，候选框不闪、不吃字、无重排抖动
- [ ] 光标在粗体标记内外移动，标记显隐不引起该行文字位移
- [ ] 拿 `art/` 里最长的一篇，滚动到底再滚回顶，无卡顿

### 1.7 实测记录

**跑出来的真数字，不是"应该"**。表格形式，与预算并列，留作回归基线。

| 指标 | 预算 | 本 stage 实测 | 上一 stage |
|---|---|---|---|
| 冷启动 → 可写 | < 1s | 780ms | — |
| 安装包体积 | — | 142MB | — |

> 没有基线就没有回归。「变慢了」这件事，只有在有上次的数字时才看得见。

### 1.8 风险与未知

本 stage 里**没干过的事**——先探还是边做边探，探到什么程度算够。Stage 2 的 IME、Stage 5 的锚点参数标定都属此类。

### 1.9 回流

**本 stage 发现的、需要回写上游文档的**：架构文档改判、纪律增删、决策修订指针、001/002 的更新。

> 实施必然会发现设计的错——本会话里「先行验证清单 4→1→0」就是这么发现的。没有这条通道，发现的错就只会留在某次对话里。

## 2. 业界实践

这类做法在 2025–2026 年长成了一个明确的门类，共识模式高度一致：**markdown 文件是真相，看板是读时视图，git 管历史**。

| 项目 | 定位 |
|---|---|
| [Backlog.md](https://github.com/MrLesk/Backlog.md) | 「管理人与 AI Agent 在 git 生态中协作」的 markdown-native 任务管理，CLI + TUI + web 看板 |
| [kanban-md](https://github.com/antopolskiy/kanban-md) | 面向自治 agent 循环的文件式看板，CLI + TUI，自带 skills |
| [claude-task-master](https://github.com/eyaltoledano/claude-task-master) | 可嵌入 Cursor / Windsurf 等的 AI 任务管理系统 |
| [Claude-Code-Agent-Monitor](https://github.com/hoangsonww/Claude-Code-Agent-Monitor) | Claude Code 的实时监控面板，含 Kanban 状态板 |

**值得注意的巧合**：这个共识——文件即真相、视图是读时生成、版本靠 git——**跟 Sepia 自己的设计是同一套**（不变量 2、D-21「图为读时视图」、D-08）。你实际上是在为造 Sepia 而先造一个小号的 Sepia。

**要不要直接用 Backlog.md？** 可以先试，但它是通用任务管理，装不下本项目特有的字段——harness 增量、反向验证记录、实测数字与预算对比、豁免计数。这些恰恰是让 stage「踏实」的部分。建议自己写一个极小的，见下。

## 3. `/harness` 看板

> **裁决（2026-08-05，用户）：看板不做，钉死。** 110 / 130 / 140 连推三次之后，第三次被问的不再是「这次做不做」而是「要不要存在」——答案是不要。stage plan 的 frontmatter 与关闭记录里的遗留债表已经让进度与债务可见，不需要单独的渲染视图。本节及下面 §4 留作推理记录，不再指导实施；债务指标（豁免趋势、反向覆盖率、dispute、实测 vs 预算）继续由 frontmatter 记录、人在关闭时抽查，不做可视化。

### 3.1 一条设计原则

**不引入第二个真相源。** 任务状态的真相就是 `specs/plan/*.md` 本身；看板只读、只渲染。理由三条：AI 改状态时改 markdown 最自然（它本来就在改文件）；git 天然给你历史与责任；人可以直接编辑而不必学一个工具。

### 3.2 数据来源

stage plan 的 frontmatter + 正文里的勾选框：

```yaml
---
stage: 2
title: 语法
status: in-progress        # todo | in-progress | blocked | done
dod: 全语法 live preview；IME 不被打断；round-trip 通过
checks_added: 4
checks_reverse_verified: 3   # 反向验证做了几条
dead_checks: 1               # 反向验证首轮空转数（口径见下）
exemptions: 2
disputes: 1                  # > 0 表示有事等人裁决
measured:
  cold_start_ms: 780
  bundle_mb: 142
---
```

**`measured` 是每个 stage 自定义的开放字典，上面两个键只是示例。** 各 stage 只填自己真正测得、且有可比性的指标——例如冷启动是 Stage 1 才有的指标，Stage 0 的窗口里没有 page 可开，照抄这个键只会写下一个没有意义的数字、污染基线。债务面板按**键名**画趋势，某个 stage 缺这个键就不画那一段，不要补零。

**`checks_added` 与 `checks_reverse_verified` 的口径（2026-08-04 钉死）**：两者都是**本 stage 新增或修改**的检查数，**不是累计**。判定很简单——**这个 stage 新写的、或改了判定逻辑的**才计入；沿用且未改动的老检查不计（它已在引入它的那个 stage 计过一次）。`reverse_coverage = checks_reverse_verified / checks_added`，**分子分母必须同口径**。

> 这条不写死就会出错，而且已经出过：Stage 1 首次回填时分母混进了 Stage 0 的四条老检查、分子只算本 stage，算出 3/19 ＝ 0.16，比真实情况悲观得多。**债务面板拿它画趋势，口径一变趋势就是假的。**
> 改了判定逻辑的老检查**要计入**（例如纪律 3 的 lint 从只扫 `.ts/.tsx` 扩到扫 `.css`）——判定逻辑变了，旧的反向验证就不再作数。

**`dead_checks` 记首轮，不记收尾**（2026-08-05 Stage 3 回流）：收尾时检查理应全部改到有效，收尾数恒为 0，没有信息量；反向验证**首轮**破坏后仍绿的条数，才是衡量检查质量的真实信号（140 §1.5 ①⑨）。

正文里的 `- [ ]` / `- [x]` 直接当子任务计数。

### 3.3 视图

四列看板（todo / doing / blocked / done），每张卡显示 stage 号、标题、子任务进度条、DoD 一句话。

**但看板本身不是重点。** 真正值钱的是旁边那块「债务面板」：

| 指标 | 为什么它比进度更重要 |
|---|---|
| **豁免总数趋势** | 只增不减 = 架构在腐化（002 §6.3）。这是最灵敏的健康指标 |
| **dispute 未裁数** | > 0 表示 AI 停在那儿等你，**每一条都是被阻塞的工作** |
| **反向验证覆盖率** | `checks_reverse_verified / checks_added` < 1，说明有检查可能是空转的 |
| **实测 vs 预算** | 哪个指标正在逼近红线，趋势比单点重要 |
| **回流待办数** | 已发现但还没回写文档的设计缺陷——它们会随时间失真 |

进度你心里本来就有数；**这五个是"看不见的债"，不做可视化就一定会积累**。

### 3.4 实现

```
harness/
  board/
    index.html          # 单文件，无构建
    serve.ts            # bun 起个静态 server，读 specs/plan/*.md
  scripts/              # 002 定义的各 check
  reports/              # 每次 check 的输出归档，供趋势图用
```

一条命令 `bun run board` 起本地服务。解析用现成的 frontmatter 解析器，渲染就是纯 HTML + 一点 JS——**不引框架、不引数据库、不做编辑**。

### 3.5 自限（重要）

`/harness` 是给 Sepia 服务的工具，**它自己不许变成一个项目**：

1. **看板不可写**。要改状态就去改 markdown。加了编辑功能就有了同步问题，就有了第二个真相源。
2. **总量控制在几百行**。超了说明在做产品而不是做工具。
3. **它坏了不影响主线**。`bun run check` 与 `bun run board` 无依赖关系——看板挂了，开发照常。
4. **不做趋势数据库**。`reports/` 就是一堆带时间戳的 json，git 管版本，要看趋势时现读现算。

> 判断标准很简单：**如果某天你开始为看板本身写测试，那它已经越界了。**

## 4. 派发与多 Claude 协作

目标形态：**你是法官与项目管理员，Claude 是执行者，板子是调度台。**

### 4.1 单一真相能不能保住？能，靠一个区分

**板子是触发器，不是状态机。**

```
markdown（任务定义与状态，唯一真相）
    ↑ 写                        ↓ 读
  Claude ←── 派发（生成 prompt + 起 session）── 板子
```

板子做三件事：读 markdown 显示、**生成 prompt 并起一个 Claude session**、把需要裁决的排成队列给你。它**从不自己写任务状态**——状态由 Claude 改 markdown 来推进，因为它本来就在改文件。这样 §3.1 的原则完好无损。

### 4.2 多个 Claude 之间怎么传信息

**session 之间没有共享内存，只能靠文件与 git。** 这是硬约束，但它带来一个好处：**每次交接都被迫留下书面记录**。

真正的坑不是"传不了文件"，是**隐性上下文传不过去**——第一个 Claude 读架构文档形成的理解，第二个得重新读。所以交接文档必须写得让「没有前文的人」能接上。

这恰好就是模板里 §1.7 实测记录、§1.9 回流的作用：**它们不是写给你看的存档，是写给下一个 session 的输入**。这个定位一变，写法就会变——会写清"为什么"而不只是"是什么"。

### 4.3 并行的单位

Stage 之间是串行的（有依赖）。**Stage 内部要并行，单位必须是「能独立成一个分支」的任务**——不是随便切。

多个 Claude 同时改同一个 repo 必然冲突，标准解法是 **git worktree**：一个任务一个 worktree、一条分支，各自跑各自的 `check:fast`，完成后合并。Claude Code 支持这种隔离。

判断能不能并行的标准很简单：**两个任务改的文件集合是否相交**。相交就串行，别赌。

### 4.4 你会在什么时候被叫醒

**这一层不需要新设计**——002 与 003 里已经定义好了全部触发器，派发系统只是把它们变成队列：

| 触发器 | 来源 | 性质 |
|---|---|---|
| `harness-dispute` 出现 | 002 §5.2 | **必须裁**，AI 已停下等你 |
| 卡住协议触发（两次失败） | 002 §5.5 | **必须裁** |
| 新增对外暴露面 | 002 §4.2 汇报格式 | 应该审 |
| 实测突破预算 | 003 §1.7 | 应该看 |
| DoD 待确认、人工验证清单 | 003 §1.6 | **必须验**，机器判定不了 |

**注意一个失败模式：如果什么都要你裁，你就成了瓶颈。** 所以三档要分清——必须裁的（上表前两行）、应该审的（默认放行但事后可见）、可自动的（`harness-exempt` 与常规实现）。这与 002 §5.2 的三种处置是同一套分级。

### 4.5 分两期，别一次做完

> 期一（看板 + 债务面板）已裁死（见 §3 头注，2026-08-05）。期二的准入条件照旧，但不再以期一为前提；真到那一步时从头评估。

| 期 | 内容 | 何时做 |
|---|---|---|
| **期一** | 只读看板 + 债务面板（§3） | **至少两份 stage plan 已回填真实实测数字之后** |
| **期二** | 派发、worktree 并行、裁决队列 | **Stage 2 之后再评估** |

**期一的准入条件也写死**（2026-08-04 修订）：原文写的是「现在，与 Stage 0 一起」，这是错的。看板的输入是 stage plan 的 frontmatter，而 Stage 0 是**第一份** stage plan——此刻只有一份数据，债务面板的五项（豁免趋势、反向验证覆盖率、实测 vs 预算、dispute 数、回流待办）全是单点，**画不出任何趋势**。而 §3.5 又要求它「总量控制在几百行」，说明晚做的代价很低。**推迟不等于搁置**：条件是「至少两份 stage plan 已回填真实实测数字」，到了就做。

理由是诚实的：**现在你还不知道真实痛点是什么。** 很可能不是"派发麻烦"——那顶多是复制一段 prompt；更可能是"我记不清上次那个 dispute 是什么了"、"这个 stage 到底验没验过 IME"。**期一恰好解决后者，且零风险。**

期二的准入条件写死，免得凭感觉上马：**手工派发已经明确成为瓶颈**（不是"感觉可以自动化"），且**至少有一次真实的多任务并行需求**（不是设想的）。

### 4.6 期二的实现纪律

真做期二时：

- **派发是薄薄一层调用**，不自己造 agent 框架——Claude Code 有可脚本化的调用方式，够用。
- **prompt 由模板 + stage plan 生成**，不手写——手写会漂移，模板才能保证每次都带上「不做什么」与「卡住协议」。
- **裁决队列可持久**：你不在的时候 Claude 停下等待，这个等待必须落盘，重启不丢。
- **一个任务的完整痕迹可回放**：输入 prompt、改了哪些文件、check 输出、最终裁决。出了问题要能倒回去看是哪一步歪的。

### 4.7 自限也要跟着升级

§3.5 的四条自限在期二仍然成立，再加两条：

5. **板子不做 agent 的编排逻辑**。判断"下一步做什么"是你的活，板子只负责让你看清楚、让派发省事。
6. **派发失败不影响手工路径**。任何时候你都能复制 prompt 自己开一个 Claude Code——**自动化是加速器，不是唯一通道**。

## 5. Stage 并行的准入与合并仪式

> 来源：Stage 2 ∥ 3 的并行实践（140 §1.1 前置〇），2026-08-05 回流落地。

§4.3 说的是 **stage 内部**的并行；**stage 之间**默认串行（有依赖），但若下面四条准入逐条成立，可以并行——这是本项目第一次双 stage 并行验出来的：

| 条件 | 怎么对 |
|---|---|
| 包不相交 | 两 stage 入驻的包集合为空集；之间若隔着「刻意不连线」的边更好——连 import 都碰不上 |
| 暴露面无重叠 | preload 白名单 / bridge 快照：至多一边动，动的那边在自己 §1.3 预先声明 |
| 共享注册表仅追加 | `dep-graph.json` / `bridge-snapshot.json` / catalog / `core/types`：两边只加不改，冲突可机械合并 |
| 人工 gate 错峰 | 两 stage 的真人验证项在时间上排开，不挤同一批 |

**合并仪式（合并者执行）**：先合并一侧进 master → 另一侧 rebase 到合并后的 master → 主干重跑**全量 `check` + 两个 stage 的全部 smoke + 涉及两 stage 的打点断言复测**。共享文件（lockfile、copy、app 装配层）的冲突按正交增量手工做并集；lockfile 冲突取一侧后重跑 install 再生成，不手合。

**仪式可经人裁跳过，但被跳项必须记债留档**（140 关闭记录先例）：跳过本身不违规，跳过而不上账才违规——否则欠的验证会在无人知晓处变成噪音。

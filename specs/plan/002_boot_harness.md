# 002 · Boot Harness：怎么保证代码真的长成 001 的样子

> 状态：v1 ｜ 2026-08-03
>
> [`001_boot.md`](./001_boot.md) 说结构**应该**长成什么样，本文档说**怎么让它真长成那样**。
>
> 前提：本项目由 AI 实施、无 code review 兜底。**架构文档里那二十多条纪律，靠读文档去守是不成立的**——AI 会读、会认同、然后在第三个文件里违反它。唯一可靠的办法是把纪律翻译成机器判定。

---

## 1. 强制力阶梯

同一条纪律，能用上面的手段就别用下面的。**越往下越依赖人的自觉，而这个项目里没有第二个人。**

| 层 | 手段 | 何时违反被发现 | 能否绕过 |
|---|---|---|---|
| 1 | **类型** | 写的时候（IDE 红线） | 要显式 `as any`，很显眼 |
| 2 | **包边界** | 编译时（import 不到）**——但有盲区**：带绑定的 `import { x } from 'pkg'` 报 `TS2307`，而副作用式的 `import 'pkg'` **不报错**，由第 4 层的 `check:deps`（`not-to-unresolvable`）兜底。`import './x.css'` 这类写法在前端很常见，别只依赖这一层 | 要改 `package.json`，很显眼 |
| 3 | **lint** | 保存 / 提交时 | `eslint-disable` 一行 |
| 4 | **专项脚本** | `check` / CI | 改脚本 |
| 5 | **单测** | `check` / CI | 删测试，**或写一条恒真的断言**（Stage 1 原子写单测曾这样空转——断言终态测不出过程；反向验证不是可选项） |
| 6 | **人工 review** | 也许永远不 | 无需绕过 |

**设计 harness 的动作，就是把纪律尽量往上搬。** 下一节做的就是这件事。

两条 Stage 2 实测得出的层级修正（2026-08-04 裁决采纳）：

- **「装饰不改字节」类性质的可测层级是 e2e，不是单测**。state 不可变使单测层的字节断言恒真（防不住任何东西）；真实字节风险在 view 层（widget 在 toDOM 里 dispatch），只有端到端 smoke 够得到。单测层放的应是「构建不抛异常 / 揭示判定正确」这类 state 可判定性质。
- **输入管线类检查必须走真实输入管线**（CDP `Input.imeSetComposition`）。DOM 合成的 `CompositionEvent` **设不动 `view.composing`**——用它写的冻结检查双重空转（Stage 2 RV③ 实测）。
- **「用户看得见」类性质的可测层级是像素，不是 DOM 属性**（2026-08-06 补，Stage 5a 真人轮实测）。
  同科的第三条：**元素挂上了、盒子非空、颜色也对，仍然可以一个像素都看不见**——
  被别的元素盖住就是了。两个常用判据都够不到这件事：
  · Playwright 的 `toBeVisible()` 只看盒子非空与 `visibility`，**盖住与否它一概看不见**；
  · `elementFromPoint` 对 `pointer-events: none` 的元素恒返回它下面那层，
    盖没盖住都报"被盖住"——拿它当判据会把人往反方向带（Stage 5a 被带过一次）。
  可用的判据只有**截图像素扫描**（解码交给 Chromium：base64 → Image → canvas → `getImageData`，
  不引图像库），或"注入前后同一区域截图逐字节比对"。
  实例：纸角警示点属性齐全、位置正确、颜色正确，而截图里那一块 **0 个 danger 像素**——
  它整个被编辑器的不透明背景盖住了（`.cm-editor` 是定位元素且排在它之后）。
  smoke 当时是绿的。**a10「首帧主题已就位（无白闪）」沿用的也是属性级断言，同科，见 160 §1.9 条目 7 的清单。**

## 2. 纪律 → 强制手段映射

架构文档 §5 的纪律表按此实现。**其中五条可以从「lint / review」升级到「类型」，那是最大的收益**——它们在写的时候就红，而不是等 CI。

### 2.1 升级为类型（最优先做）

| 纪律 | 类型怎么表达 |
|---|---|
| registry 存 key 不存字符串 | `title: CopyKey`（`keyof typeof copy` 的联合），传字面串编译不过 |
| AgentBridge 每请求带 `directory` | 该参数**必填**且类型为 `BookDirectory` 品牌类型，忘了编译不过 |
| system prompt 必须是常量 | 类型为 `const` 断言的字面量联合，模板字符串拼变量赋不进去 |
| ~~组件不得出现字面色值~~ **改判：维持 lint** | **类型层够不到它。** React 的 `style={{ color: '#fff' }}` 走 `CSSProperties`，类型上就接受任意字符串，`ThemeVar` 拦不住。`ThemeVar`（`\`var(--${string})\``）保留，但定位为 **token 词汇表**而非强制手段；纪律 3 的强制手段仍是 lint，并扩到扫 `.css`（只放过调色板文件）。**仍是「一条纪律一种手段」** |
| 落笔前做 CAS 校验 | 落笔函数**只接受** `{ range, expectedText }`，不提供无校验的重载 |

**最后一条是模式而非技巧**：把危险操作设计成"没有不安全的调用方式"。不安全的路径不存在，就不用检查它有没有被走。

> **一条元教训（2026-08-04，Stage 1 实测）**：上表原有五条，是在**没有检验「类型能不能真的够到那个危险」**的情况下写下的。字面色值那条一落地就发现够不到——`CSSProperties` 是个洞。**升级为类型不是越多越好：用覆盖面更小的手段换掉更大的，是净退步。**
>
> 剩下三条（`BookDirectory`、system prompt 常量、落笔 CAS）在 Stage 3 / 4 落地**之前**，必须先各问一遍同一个问题：**这个类型是危险操作的唯一通道吗？有没有一条绕过它的合法写法？** 答不上来就别升，留在原来的层。
>
> **第二条元教训（2026-08-05，Stage 3 反向验证实测）**：品牌类型**默认是空转的**——生产路径全经构造函数（`asBookDirectory`），类型放宽没有可观测差别，typecheck 照绿。**类型层纪律一律配一份 `.test-d.ts` 负向断言**：用 `@ts-expect-error` 把「裸值必须编译不过」本身变成断言——类型一放宽，tsc 立刻报「无用的忽略」。`BookDirectory` 已按此落地（Stage 3），Stage 4 的类型层第四五条上来就要带，不等反向验证再发现（140 §1.5 ①）。

### 2.2 由包边界强制

`core` / `editor` / `agent` / `ui` / `app` 的依赖图（001 §2.2）。`core` 的 `package.json` 不声明 `electron`，就 import 不到——这是编译期物理约束。

**外加一条脚本校验**：`check:deps` 用 dependency-cruiser 断言实际 import 图与 001 §2.2 的图**完全一致**，包括那两条"刻意不连线"（`editor ↮ ui`、`editor ↮ agent`）。配置文件本身就是依赖图的机器表达——**图变了就改配置，改配置就会被 diff 看见**。

### 2.3 由 lint 强制

| 纪律 | 规则 |
|---|---|
| 组件不得 import `window.api` / 不直接请求引擎 | `no-restricted-imports`：组件目录禁 import `preload`、禁 `fetch` |
| Sepia 自有文件的路径只由 `paths.ts` 派生 | 两支正则：**XDG 变量名**（`XDG_*`）只许出现在 `services/paths.ts`——指向哪才是纪律关心的事，而那只有在派生点看得出来；**XDG 根字面量**（`.config/sepia`、`Library/Application Support`…）**含 `paths.ts` 在内哪里都不许**，因为 120 §1.1 问题七 那个 bug 真要重演，重演的地点恰恰就是 `paths.ts` |
| `.sepia` 下 json 原子写 | 禁在 services 之外直接 `fs.writeFile` |
| 日志不记凭据 | 禁 `log(process.env)` 与 `JSON.stringify(process.env)` |
| 组件不得出现用户可见字面串 | 中文字面量检测（弱规则，允许标注豁免） |

### 2.4 由专项脚本强制

| 脚本 | 断言 | 归属 | 进 `check`？ |
|---|---|---|---|
| `check:bridge` | preload 暴露面与快照一致；新增须显式更新快照并在 diff 中可见 | Stage 0 | 是，gate |
| `check:deps` | 实际依赖图 == 001 §2.2 的图 | Stage 0 | 是，gate |
| `check:workspace` | `vendor/` 不被任何 workspace glob 匹配 | Stage 0 | 是，gate |
| `check:theme` | Shiki 与 CM6 的 token 色值表由同一份色板派生（比对生成结果） | **Stage 2**（有色板时） | 是，gate |
| `check:artifacts` | 构建产物中 `.wasm` 四份齐全、`.node` 数量为零 | **Stage 3**（有产物时） | **是，gate**（2026-08-05 改判：新鲜 checkout 首跑即抓到「产物未构建」的红，150 §1.1；原排「只进 CI」作废） |
| `check:patches` | 统计 `patches/opencode/` 数量并打印——**不阻塞，只让增长可见**（T-18 的健康指标） | **Stage 3**（有 `patches/opencode/` 时） | **不是 gate**——是 `check` 输出里的一行数字，不影响 PASS/FAIL |

**「不是 gate」这一档要单列出来**：`check:patches` 若按 gate 实现，它要么恒绿（等于 §6.2 说的净负担），要么给 patch 数设一个武断的上限。它的价值全在**让数字被看见**，所以它的正确形态是 `check` 末尾多打一行，以及债务面板上的一条趋势线。

### 2.5 由测试强制

round-trip 字节保真 ｜ composition 活跃期间装饰冻结 ｜ watcher 自写回声抑制 ｜ 落笔 CAS ｜ 锚点三级对齐 ｜ 启动 t0–t5 打点在预算内 ｜ GitService 串行队列。

## 3. 一条命令

```
bun run check
```

= `lint` → `typecheck` → `check:deps` → `check:bridge` → `check:workspace` → `test`（turbo 按包并行）

**这是 AI 与 CI 共用的唯一入口。** 它必须满足三条，否则形同虚设：

1. **快**——目标 30 秒内。慢了就没人（也没 AI）在提交前跑。**计时口径（2026-08-04 写死）**：冷测＝`.turbo` 与 `*.tsbuildinfo` 一并清掉后测；增量化的收益单列 warm 口径记录，两条数字并行，防止趋势断裂。typecheck 增量化在 **Stage 2+3 合并仪式前**完成。
2. **输出可判定**——最后一行是 `PASS` 或 `FAIL: <哪条纪律>`，不要让人从一屏日志里找。
3. **失败信息指向纪律编号**，而不只是报错行。`FAIL: 纪律 3（字面色值）— packages/app/src/x.tsx:12`，AI 才知道去读哪一条。

smoke 要起真应用，只进 CI。`check:artifacts` 原排「只进 CI」，Stage 3 实际纳入了 gate、2026-08-05 改判留用——引擎产物是本地开发的前置，新鲜 checkout 首跑它真抓到过「产物未构建」（150 §1.1）。

## 4. `CLAUDE.md` 怎么写

### 4.1 它的角色

CLAUDE.md **不是检查，是导航与前置约束**。检查告诉 AI「你错了」，CLAUDE.md 让它**一开始就别走错**。两者互补，缺一不可：只有检查，AI 会反复试错；只有 CLAUDE.md，它会遗忘。

三条写法纪律：

- **短**。目标 150 行以内。太长 AI 就只读开头。**链接而不内联**——正文只放"做什么"，"为什么"留在架构与论证文档里。
- **每条纪律注明由谁强制**。写「不得出现字面色值（lint 规则 3）」比写「请使用主题变量」有用得多——AI 知道这条会被机器抓，就不会赌。
- **给正误对照，不给说教**。`❌ color: '#fff'` / `✅ color: 'var(--ink)'` 一行顶三段解释。

### 4.2 骨架

```markdown
# Sepia

一句话定位 + 指向 specs/design/sepia-architecture.md

## 动手前必读（按序，别全读）
1. specs/design/sepia-architecture.md §1 约束 §5 纪律   ← 每次都读
2. specs/plan/001_boot.md §2 依赖方向                   ← 碰结构时读
3. 当前 stage 的验收条件                                 ← 每次都读

## 五条不可协商（违反即回退，不要商量）
1. 纸永远可写，Agent 可以缺席
2. 未触及的字节逐字节保留
3. AI 不抢笔：写入正文必经用户落笔
4. Agent 无写权限
5. 只发明徽章与思维链

## 依赖方向（由包边界与 check:deps 强制）
core ──→ editor ─┐
  └───→ agent ───┼──→ app
        ui ──────┘
两条刻意不连线：editor ↮ ui、editor ↮ agent

## 常见违规对照
❌ import { api } from '../preload'      ✅ import { api } from '@/services/api'
❌ color: '#fff'                          ✅ color: 'var(--ink)'
❌ registerCommand({ title: '加粗' })     ✅ registerCommand({ title: copy.cmd.bold })
❌ fs.writeFile(jsonPath, ...)            ✅ atomicWrite(jsonPath, ...)
❌ send(threadId, parts)                  ✅ send(threadId, parts, { directory })

## 完成前必须
bun run check:fast   # 每次改动，必须绿
bun run check        # stage 收尾，必须 PASS

## 卡住协议
连续两次都无法在不违反纪律的前提下完成 → 停下，不要第三次。
报告：想做什么 / 撞到哪条纪律 / 两次分别试了什么 /
      判断是纪律错了（用 harness-dispute）还是实现方式错了

## 三种记号，别用混
// harness-exempt: <号> <理由>   纪律对、此处例外——可自行处置
// harness-dispute: <号> <论据>  认为纪律本身有问题——停下报告，不得自行处置

## 汇报格式（每次改动后）
- 改了哪些文件
- check 的最后一行
- 是否新增了对外暴露面（preload / 包依赖 / 配置字段）
- 是否有 spec 需要同步更新
```

### 4.3 「汇报格式」是最容易被低估的一节

它把**自证**变成流程的一部分。尤其是第三条——**新增对外暴露面必须自己说出来**。preload 白名单、包依赖、配置字段，这三样是架构侵蚀最常见的入口，而它们单看每一次都"只是加一个"。要求主动申报，等于让侵蚀在发生的当时就可见，而不是三个月后回头发现白名单有四十项。

## 5. 当 harness 挡路时

**会挡路，而且会挡到任务做不完——这是真实风险，不是假想。** 但要看清：让任务卡死的通常不是「检查太严」，严只会让人变慢；**卡死的是「没有表达『这条纪律错了』的方式」**——那时 AI 只剩两个选择，违反（被挡）或放弃。

### 5.1 五种真实失败模式

| 模式 | 表现 | 为什么危险 |
|---|---|---|
| **纪律与需求真冲突** | 写纪律时的理解不完整，Stage 4 才发现某功能非违反不可 | 正确解法是**改架构**，但 AI 不会自己去改，它会试图绕过或卡住 |
| **harness 自身有 bug** | 正则误报、依赖图配置写错、对合法写法误判 | **AI 倾向于相信工具而不相信自己**——它会把正确的代码改坏，只为让红变绿 |
| **粒度太粗，无法表达合法例外** | 「禁中文字面串」撞上错误信息模板；「禁 `fs.writeFile`」撞上迁移脚本 | 逼出大量豁免，豁免多了就没人看 |
| **长程任务的中间态** | 跨包重构做到一半，包 A 已改包 B 未跟上，全量检查必红 | 若要求每步全绿，**AI 会退化成只做一步能完成的小改动**，架构演进就此停滞——最隐蔽的一种 |
| **检查比文档更新得慢** | 架构已改判，lint 规则还在拦旧写法 | 制造「文档说可以、机器说不行」的死锁 |

### 5.2 三种处置必须分清

我原先只设计了一种豁免，**那是缺陷**。实际需要三种，性质完全不同：

| 记号 | 含义 | 谁能决定 |
|---|---|---|
| `// harness-exempt: <纪律号> <理由>` | **纪律对，此处是合法例外** | AI 可自行处置，计入豁免总数 |
| `// harness-dispute: <纪律号> <论据>` | **认为纪律本身有问题** | **AI 不得自行处置**——停下来报告，等人裁决 |
| `SEPIA_HARNESS_BYPASS=1` | 临时跳过全部检查跑通别的 | 大字警告 + 记录到文件，**只用于本地探索，CI 恒忽略此变量** |

**记号里的纪律编号要写全**（`harness-exempt: 纪律 20 <理由>`），裸数字不匹配。Stage 3 一次实测踩出两个坑：`check-discipline` 曾把剥掉注释后的行传给豁免匹配，而记号本身住在注释里——豁免机制从未生效；修为「违规匹配用剥后行、豁免匹配用原始行」后才真生效（140 §1.7）。

**第二种是关键。** AI 最容易犯的错，是把「我觉得这条纪律不对」当成第一种处理——打个豁免继续走，架构就被悄悄改了，而且改得毫无痕迹。分开之后，「纪律错了」变成一次必须升级到人的事件。

`bypass` 不堵死也是有意的：**堵死会让人去改检查脚本本身，那比临时绕过糟得多**——脚本被改坏是永久的，绕过是一次性的。

### 5.3 纪律要分硬度

现在架构文档 §5 那 22 条是平的，这不对。三档：

| 硬度 | 内容 | 豁免 |
|---|---|---|
| **不变量级** | 五条不变量的直接体现：字节 round-trip、落笔 CAS、Agent 无写权限 | **无豁免**。冲突即任务失败，必须先改架构 |
| **纪律级** | 其余大部分 | 可 `exempt`，计数 |
| **约定级** | 命名、目录习惯 | 建议，不阻塞 |

判断标准：**违反它会不会让用户丢字节或被 AI 抢笔**。会 → 不变量级。

**一条检查里混着两档硬度时，把不变量级的子条单列成独立检查**，不要给同一条检查标两个硬度。理由是豁免语义：硬度决定能不能 `exempt`，而「这条检查可以豁免一半」是无法表达的——一旦允许，`harness-exempt` 就会被用来绕过不变量级的子条，而它本该无豁免。

典型例子：`check:bridge` 本体是纪律级（暴露面与快照一致），但「preload 不得暴露任何绕过落笔 CAS 或给 Agent 开写路径的通道」直指不变量 3 与 4，是**不变量级**。**Stage 3 桥上出现第一个引擎通道的当天，必须把这一子条拆成独立检查。**

### 5.4 长程任务的中间态

分两级，这条直接决定跨包重构做不做得成：

```
bun run check:fast     # 类型 + lint，秒级 —— 每次改动跑，必须绿
bun run check          # 全量 —— stage 边界跑，必须绿
```

**中间态允许 `check` 红**，但必须在 stage 结束前归零。不给这个空间，大改就永远做不成。

### 5.5 卡住协议（写进 CLAUDE.md）

> 若连续两次尝试都无法在不违反纪律的前提下完成任务：**停下来，不要第三次尝试。**
> 报告：想做什么 / 撞到哪条纪律 / 两次分别试了什么 / 你认为是纪律错了还是实现方式错了。

这防止两种浪费：在死胡同里烧 token，以及最终选一个破坏性方案交差。

### 5.6 纪律与检查必须原子更新

**改纪律的那次提交，必须同时改对应的检查。** 否则必然出现文档与机器打架。反过来也成立：**发现检查有 bug 时，先问这条纪律还成不成立**——很多"误报"其实是纪律没想清楚的信号。

## 6. harness 自身的纪律

**harness 不能比被约束的代码还重。** 三条自限：

1. **一条纪律只用一种手段**。既写类型又写 lint 又写测试，改一次要改三处，最后没人维护。选阶梯上最高的那一层，其余删掉。
2. **新增检查必须能指出它抓到过什么**。抓不到真实违规的检查是净负担——它只会在无关改动时变红，训练人去忽略红色。

   **推论（2026-08-06，150 债 8）：破坏方式必须瞄准「真正会出事的那个场景」，而不是功能的一般路径。**
   一条检查沿着 happy path 破坏仍然绿，不是运气差，是**它测的根本不是会出事的那个场景**。
   反向验证要先问一句「这条检查要防的事故长什么样」，再照着那个样子去破坏——
   照着功能的一般路径破坏，验的是功能还在不在，不是检查有没有效。

   > 典型形态：**桩替被测系统假设掉的那部分，正是检查最容易空转的地方。**
   > 桩总是走通的那条路，于是"走不通"的分支从来没被这条检查看见过。

   **四例索引**（全部来自 150，`dead_checks: 4` 的明细在 150 §1.5）：

   | 例 | 破坏后仍绿，因为 | 改成什么才红 |
   |---|---|---|
   | #4 落笔原子性 | 沿一般路径验「撤销之后文字没了」——拆成两个 transaction 时它照样没了 | 验**撤销一次的结果**（半截态才是事故），不是撤销之后的最终态 |
   | #7 流式单调 | 「允许揭示回退」只在**回退真的发生**时才看得见，而桩的文本恒增 | 桩造一次回退，断言揭示不跟着退 |
   | #9 全链打点 | 吞掉 m4 仍绿——没有人在看**完整的那条时间轴**，只看了各点存在 | 断言六点齐、同一条时间轴、顺序单调 |
   | #17 回声不成为结果 | 回声一到就被助手文本覆盖，检查那一刻它早已不在 | 桩加 `silent` 模式（只回声、模型不答）——**这才是出事的那个场景** |
3. **允许豁免，但豁免要显眼**（§5.2 的三种记号），并由 `check` 统计总数。**豁免数只增不减就是架构在腐化**，这个数字比任何单条检查都更能说明健康状况。

## 7. 落地顺序

harness 与 001 的 Stage 0 一起做，但**不必一次做全**：

| 时机 | 做什么 |
|---|---|
| Stage 0 | 包边界、`check` / `check:fast` 两级骨架、`check:deps`、`check:bridge`、`check:workspace`、三种处置记号、CLAUDE.md 初版（含卡住协议） |
| Stage 1 | 类型层**两条**（`CopyKey`、`ThemeVar`）、启动打点断言、纪律 20 由 review 升 lint。**升 `ThemeVar` 的同时删掉纪律 3 的 lint 规则**（§6.1 一条纪律只用一种手段） |
| Stage 2 | round-trip、composition 冻结、`check:theme` |
| Stage 3 | 类型层第三条（`BookDirectory`：AgentBridge 每请求必带 `directory`）、`check:artifacts`、`check:patches`、**`check:bridge` 的不变量级子条单列** |
| Stage 4 | 类型层第四、五条（system prompt 常量字面量联合；落笔只接受 `{range, expectedText}`，不提供无校验重载）——**一上来就带 `.test-d.ts` 负向断言**（§2.1 第二条元教训） |
| Stage 5+ | 各 stage 引入自己的纪律与检查，随功能一起长 |

> **§2.1 那五条不是同一个 stage 能做完的**——每条都要等自己的宿主类型先存在。原先笼统排在 Stage 1，实施时会发现三条无处可依，然后要么硬造宿主、要么静默跳过（后者更可能）。

> **Stage 0 实况**：字面色值（纪律 3）、组件不碰 `window.api`（纪律 1）、日志不转储 `process.env`（纪律 18）、下层四包不 import 进程侧代码（结构 3）这四条**提前到 Stage 0 落地**了，实现在 `scripts/check-discipline.mjs`，作为 `lint` 的第一步跑——所以它们在 `typecheck` 之前就给出带编号的失败信息。
>
> 纪律 3 在 §2.1 里本打算升级成类型（`ThemeVar`）。Stage 1 建主题变量表时**二选一**：升类型就把 lint 规则删掉，别两头都留（§6.1，一条纪律只用一种手段）。
>
> `check:artifacts` 随 Stage 3 的 vendor 构建一起加，**实际进了 `check` gate**（与这条原议相反，§2.4 已改判——它抓到过真问题）。smoke 仍只进 CI。

**原则：一条纪律在被写进架构文档的同一时刻，就要决定它由谁强制。** 没有强制手段的纪律，等于没有这条纪律——它只是文档里的一句愿望。
